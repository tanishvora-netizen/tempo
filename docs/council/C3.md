# Council C3: the UI

Question: does the UI make the demo path obvious, every number trustworthy and traceable, and the screens usable at 1440 and 1024 px?
Members: council-design, council-judge, council-controller.
Screenshots: `docs/screenshots/*-1440.png` and `*-1024.png` (taken by `scripts/screenshots.py` after the final precompute).

## Chair's position (written before reading any verdict)
The overview is dense without being cluttered. The pointwise band is labeled as such, with the any-day breach probability beside it. The comparison with today's weekly run and greedy sits right next to the chart, and the week's run with Approve and the autonomy setting sits below. My concerns:
1. The overview tries to carry the whole story; the what-if and proof screens must be one click away and look like the same product.
2. Status chips ("Parser only" vs "Verified") need a one-line legend, or a judge will read "Parser only" as weaker.
3. The KPI "Cost of cash" needs its formula on hover.
4. At 1024 px the run table must keep vendor, amount, decision, and value visible without horizontal scroll.

## Raw verdicts

### council-design: FIX
1. Same bill shows two annualized returns (bill-panel-1440: 37.2%/yr in the grid and Return column, 33.8%/yr in the sentence). Fix: one definition (cash return) everywhere; label the textbook rate if kept.
2. Needs-review count disagrees with itself (badge 12, filter 13, subhead 13; demo script says 13); screenshot runs share state. Fix: one count of unresolved items; reset state before each screenshot run.
3. Decimals change within a column (+$360 next to +$92.67), mixed K precision, cost of cash 17.0% / 17% / 17.01%, threshold "25000". Fix: whole dollars in tables with exact tooltip, one decimal on K/M, one percent formatter, formatted threshold.
Smaller: at 1024 the Why and Rail columns disappear; the legend swatch "2/10" next to "Local model / Gave no reading"; raw "ollama transport error: timed out" text.
Missed by others: future-dated invoices and emails (Nov 16 invoice, Dec 12 email) on a Nov 10 plan with no explanation in the UI. Fix: an "Expected, issues <date>" chip and a one-line note.

### council-judge: FIX (demo readiness 6/10)
1. Two returns for the same bill (table 37.2% vs sentence 33.8%; script example 36%). Fix: `_decision` uses `cash_return`; update the script.
2. "Late 0" and "No bill is paid late" beside five bills whose reasons say they arrive after the due date (one reason contradicts itself). Fix: label "arrives after due", count them, reword the overview check.
3. What-if form shows Bluefin while the Copperline preset is selected; a "4 bills would be paid after their due date" banner sits beside "Certified" while the script says "still certified"; raw transport error; a December email on a Nov 10 plan. Fix: sync the form, explain late bills, plain model status, explain dates.
Missed by others: the KPI tiles don't add up (discounts + rewards = $45.9K vs value $41K; the $4.9K gap is yield forgone and surcharges). Fix: show the breakdown.
Also: the smart spreadsheet earns more ($50.2K at 4.83%); Tempo's win is certifiability, so lead with that.

### council-controller: FIX
1. The approval covers more than the dialog shows: the dialog says 25 bills / $662,379 but the request carries no scope and the audit entry and payload cover the whole 13-week plan; the approver is a typed name with no separate preparer. Fix: send and hash the week's bill ids and total; limit the payload to them; label the name as attested, not authenticated.
2. Two returns for one bill (37.2% grid vs 33.8% sentence). Fix: effective return everywhere, nominal as a footnote.
3. RTP plan vs payload and vendor: Juniper accepts ACH, the plan sends RTP on the deadline, the PATCH says ACH, and the "confirm RTP" note appears only after approval. Fix: show the count of RTP-dependent bills in the approve dialog before the button.
Missed by others: as ACH from Nov 10 the Juniper payment arrives Nov 16 (Veterans Day), after the deadline, so the company would short-pay $1,991 without earning the discount; at 1024 px the Rail column is hidden.

## Consensus
All three caught the two-returns contradiction. The design is strong; the gaps are consistency (counts, formats, returns), honest labeling (late arrivals, expected bills, RTP dependency, model status), and an approval that must cover exactly what the approver saw.

## Strongest dissent
Controller: an approval that records more than it displays is an audit failure, not a UI nit.

## Chair's rulings
| # | Item | Ruling |
|---|---|---|
| 1 | One annualized return | Accept. `Decision.annualized_return` is now the return on cash actually paid; the textbook rate ships as `terms_rate` for a footnote. |
| 2 | Late arrivals | Accept. Rows carry `arrives_after_due`; KPIs carry `arrive_after_due_count`; reasons for these bills say "the earliest a bank payment can arrive"; the UI labels and counts them. |

| 4 | Approval scope | Accept. Approve sends the bill ids; the audit entry records count, totals, RTP-dependent count, and a hash of the ids, with `approver_authenticated: false`; the payload preview covers only the last approval. |

| 6 | Review count | Accept. One source (`review_count`); screenshot runs reset state first. |
| 7 | Expected bills | Accept. Rows carry `expected`; UI chip and note. The generator is unchanged (re-dating emails would invalidate the model cache). |

| 10 | Lead with certifiability | Accept. The demo close says so; the sensitivity row backs it. |
