# Council C1: scope, data model, formulation

Question: is this the right scope, data model, and formulation for a 4-minute demo to Ramp engineers?
Members: council-judge, council-ramp-engineer, council-quant.
Files: `docs/BUILD_DIRECTIVE.md`, `docs/superpowers/specs/2026-11-10-tempo-design.md`, `docs/DECISIONS.md`.

## Chair's position (written before reading any verdict)
Scope is right if the demo path is ruthlessly one flow: Overview (fan + KPIs) to Payment run row explanation to What-if preset to Proof panel. The biggest risk is not the math but breadth: eight loop steps, five screens, two drawers, three providers. I will protect the optimizer, certification, Needs review, and the proof panel, and cut in the directive's order. Formulation: the reduced SAA with a quantile cut is exact and small; the real honesty risk is the evaluation's dependence on our own forecast model (scenarios C come from the same model we fit), which must be named as the main weakness. Data model risk: future-dated "open" bills need a plain explanation.

## Raw verdicts

### council-judge: FIX (demo readiness 3/10, no code yet)
1. The strongest simple alternative is missing as a baseline. A spreadsheet rule ("take the discount if its annualized return beats the cost of cash and the P5 balance path stays above the buffer, due-date order") is not among the policies; `greedy_discount` and `deterministic_p50` both plan on P50, so beating them proves little, and the Bonferroni ablation that comes closest is on the cut list. Fix: add `greedy_p05` as a sixth policy, take the ablation table off the cut list, report MILP dollars over `greedy_p05` at a safe breach rate.
2. Claims about Ramp made to Ramp engineers need sources (BUILD_DIRECTIVE.md:76-81): undocumented `EARLY_PAYMENT_DISCOUNT`, Billhop date, $0.59 ACH fee, Ramp AR Sept 2026, Faster Payments ~1%. Fix: `docs/SOURCES.md` with URL and check date per claim; reword "none of these decides" to "no public API field or documented feature we found"; ask about the enum only as a question.
3. The demo is too long for 4 minutes (8 loop steps, 5 screens, 2 drawers, 3 handoffs). Fix: script ingest, plan, what-if preset, proof, approve; leave negotiation and audit for Q&A.
Missed by others: a live custom what-if shows an uncertified in-sample breach number (certification needs up to 5 solves plus a fallback). Label it "uncertified, in-sample" or recount on seed B live. Also `AS_OF` Nov 10 means some plan dates are in the past at the Nov 19 final; say so.

### council-ramp-engineer: FIX
1. The data model is unverified against Ramp's docs (no snapshot of llms-api.txt, no ruling on field names, `payment_method` enum, hold/release paths, the `EARLY_PAYMENT_DISCOUNT` claim). Fix: save the schema to `docs/ramp_api_snapshot.md` with the retrieval date; test that every key and enum in the payload preview appears there; drop the judge question if the enum is not in the snapshot.
2. Options are defined by arrival date but Ramp's `payment_date` is the send date. Fix: `PaymentOption` gets `send_date` and `arrival_date`; PATCH uses `send_date`; plan early ACH with the 4-business-day upper bound; test both.
3. Determinism vs `time_limit` (CPU-dependent plans; no same-seed hash test). Fix: bound effort (`node_limit`), keep `time_limit` as a safety net, hash canonical JSON with no floats, test two runs give one hash.
Missed by others: Nov 11, 2026 (day 1) is Veterans Day, a Federal Reserve holiday (also Thanksgiving, Dec 25, Jan 1, MLK in the horizon); holiday list in assumptions.py as SOURCED with a test around Nov 11. The payload preview has hold but no release; approving a Needs-review item should produce a release request.

### council-quant: FIX (core math numerically checked: 37.24%, 36.73%, 44.59%, d* 0.6532%, Wilson 464 pass / 465 fail; quantile cut valid; M = q - R tightest; Luedtke reduction applies since G is scenario-independent)
1. The certification loop tests up to six plans on B with no multiplicity correction: ~27% chance one wrongly passes if all are at 5%; a plan passing B just under the line fails on C about half the time. Fix: Bonferroni z = 2.394 (0.05/6) on B; the B test is the pass/fail check and C is reported as it comes out.
2. Binding-reason check order is wrong: a tight plan sits at exactly K breaches, so switching nearly any bill early exceeds K and economic losers get labeled "cash binds". Fix: first compare v_early <= v_chosen (economic); only when the early option is worth more, recount. Compare economics against YIELD_ON_CASH, which the objective uses.
3. Forecast underspecified: pool sigma from within-customer residual variance (total spread overstates); sample the truncation with `norm.isf(u * sf(e))`; the K = 0 fallback to N = 1,000, K = 20 is looser (2% > 0%); use N = 1,000 with K <= 5.
Missed by others: seeds B and C come from the fitted model, so certification ignores fit error and the SIGMA_MACRO assumption; also draw C from the generator's true model and report both. Calibrating starting cash on seed C reuses the reported numbers; calibrate on a separate seed D.

## Consensus
The math core is sound (quant verified the formulas and the reduction). All three ask for more honesty at the edges: sourced claims, uncertified numbers labeled, multiplicity on the certification test, a stronger simple baseline, and evaluation against the true data-generating process.

## Strongest dissent
Judge: without a P5-aware greedy baseline, "why a MILP?" has no answer. This is the most important addition.
